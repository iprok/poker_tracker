# Первый этап: тесты Telegram-бота и Python 3.14

Схема БД не изменена. Выход без закупа в текущей игре запрещён; активная игра
восстанавливается из БД при закупе и выходе; флаг подтверждения завершения очищается. Dockerfile использует Python 3.14.
Обновлены зависимости, необходимые для совместимости; версия Telegram-библиотеки
повышена с 22.0 до 22.8, в том числе ради запуска polling без заранее созданного
цикла asyncio в Python 3.14.

## Запуск

Из корня проекта, в отдельном окружении Python 3.14:

```sh
python3.14 -m venv /tmp/poker-tests-314
/tmp/poker-tests-314/bin/python -m pip install -r requirements.txt
make test PYTHON=/tmp/poker-tests-314/bin/python
/tmp/poker-tests-314/bin/python -m pip check
```

Или в собранном Docker-образе (не запускает polling):

```sh
docker compose -p poker-bot build python_bot_poker
docker compose -p poker-bot run --rm --no-deps python_bot_poker python -m unittest discover -s tests -v
```

Используется стандартный unittest: дополнительных тестовых зависимостей нет.
Набор следует запускать отдельным процессом указанной командой. Перед импортом
приложения он переходит во временную директорию, создаёт вымышленные настройки и
отдельную SQLite-базу; между тестами таблицы пересоздаются. Telegram заменён
AsyncMock, TCP-соединения запрещены. Рабочие config.json и poker_bot.db не читаются.
Проверки вызывают реальные обработчики, декораторы доступа и репозитории.
Это интеграционные проверки текущего поведения, пока не модульные тесты домена.

## Зафиксированные правила

Тестовая конфигурация: 3000 фишек = 1 EUR, шаг выхода 1500 фишек.
Рабочие суммы по-прежнему определяются вашим config.json.

- Закуп требует активной игры в базе; повторный закуп — новая запись.
- Повторный старт не создаёт вторую игру. После потери контекста /startgame
  восстанавливает идентификатор незавершённой игры из базы.
- Выход записывает фишки и их денежный эквивалент; нулевой выход допустим.
- Отрицательный остаток, нарушение шага и превышение оставшегося банка отклоняются.
- Предыдущие выходы уменьшают доступный банк.
- Баланс учитывает закупы и выходы; сводка разделяет должников и получателей.
- Запрос подтверждения выхода сам по себе ничего не списывает; отмена не пишет
  операцию, повторное подтверждение уже выполненного выхода её не дублирует.
- Завершение игры требует подтверждения; отмена оставляет игру открытой.
- Новая игра получает отдельный идентификатор; закуп после завершения отклоняется.
- Закуп недоступен неучастникам групп и вне личного чата с ботом.
- Приложение создаётся, polling проходит начальную инициализацию без существующего
  event loop. В этом тесте инициализация Telegram подменяется, затем запуск сразу
  останавливается: настоящее получение сообщений он не проверяет.

## Проверка на игре во вторник

До игры сохраните предыдущую рабочую версию/образ и сделайте согласованную
резервную копию SQLite через backup API или при остановленном боте. Обновите
окружение заранее и запустите тесты. При Docker нужно пересобрать образ:
одного restart недостаточно для смены Python и зависимостей.

На настоящей игре проверяйте только реальные операции, не добавляя фиктивные закупы:

1. /startgame, затем /menu: игра открывается, меню отображается.
2. При первом закупе и докупе: запись и итоговая сумма совпадают с реальными фишками;
   сообщения доходят в личный чат и канал.
3. /summary: закупы всех игроков и банк сходятся с учётом организатора.
4. При реальном выходе: сначала отменить подтверждение и убедиться по /log,
   что выхода нет; затем подтвердить правильный остаток. Проверить сумму и баланс.
5. Если кто-то проиграл весь стек, проверить выход с нулём.
6. После расчётов проверить /summary и /log; завершить игру с подтверждением.

Дополнительно проверьте: игрок без закупа получает отказ при выходе, даже с нулём;
после перезапуска закуп работает без повторного /startgame. Запишите расхождения, текст команды,
ожидаемый и фактический результат, время события. При проблеме остановите новую
версию и верните сохранённую рабочую версию/образ. Схема БД не менялась, поэтому
при откате кода можно оставить текущую базу. Не восстанавливайте старую копию поверх
новых игровых записей: это потеряет операции, проведённые после копирования.

## Границы и вопросы для следующих этапов

17 тестов прошли на Python 3.14.6; pip check не обнаружил конфликтов.
Docker-образ в этом окружении не собирался; реальный Telegram не запускался.
Турнирные сценарии, /ludoman, все варианты команд и конкурентные операции пока
не покрыты. Эти проверки не означают полное покрытие бота.

При чтении кода отмечены вопросы, которые сейчас не исправляем и не объявляем
правильными правилами:

- Повторные частичные выходы после закупа пока разрешены при наличии фишек
  в банке. Менять это правило отдельно пока не договаривались.

Следующий этап — выделить сценарий закупа, сохранив эти проверки как защиту от
регрессий. Устаревший импорт declarative_base заменён на sqlalchemy.orm; предупреждение устранено.

## Второй этап: выделение сценария закупа

`BuyinUseCase` в `domain/use_cases/Cash/buyin_use_case.py` находит активную игру,
записывает закуп через репозиторий и возвращает неизменяемый `BuyinResult`:
идентификатор игры, фишки, стоимость, количество закупов игрока и их общую сумму.
Сценарий не обращается к Telegram и не читает глобальный config.json.
Параметры закупа и репозитории передаются в конструктор.

Telegram-обработчик отвечает за доступ, получение имени, вызов сценария,
обновление контекста и отправку прежних сообщений. Граница транзакции задаётся
через `Session.begin()`: запись закупа и получение итогов завершаются вместе;
при ошибке запись откатывается. Отправка сообщений происходит после коммита.
Остальные сценарии и схема базы не изменены.

Добавлены четыре проверки сценария без Telegram: отсутствие активной игры,
первый и повторный закуп, разделение итогов по игрокам и играм, откат при ошибке.
Всего проходят 21 тест на Python 3.14. Эти новые проверки используют реальную
временную SQLite-базу, как и исходный набор.

На пятничной игре проверить первый закуп и докуп, закуп другого игрока,
личные сообщения, сообщения в канал и автоматическую сводку. Суммы, тексты
и команды должны остаться прежними. При перезапуске следующий закуп должен
попасть в существующую игру без дополнительного /startgame.

## Различение игроков в сводке

Сводки текущей и прошлых игр считают баланс по Telegram ID. Одинаковые имена
не объединяют игроков, а смена имени не разделяет операции одного игрока.
При совпадении имён добавляется @username, а при его отсутствии или ошибке
Telegram — ID. Для уникальных имён формат остаётся прежним.
Если Telegram недоступен, используется первое непустое сохранённое имя игрока,
при отсутствии имени — ID. Миграция данных не требуется.

Добавлены три проверки: разные балансы тёзок, смена сохранённого имени при
недоступном Telegram и различение тёзок через ID. Всего проходят 24 теста.
На игре проверить /summary и /summarygames для игроков с одинаковыми именами.

## Автозавершение кеш-игры

В `config.json` можно добавить `"announce_game_duration": true`, чтобы каждые
30 минут отправлять длительность игры в основной кеш-канал (`channel_id`).
По умолчанию эта опция выключена. Она не отключает предупреждения и автозавершение.

Первая проверка назначается через 30 минут от начала игры. При банке меньше
2 EUR (закупы минус выходы) или длительности строго больше 12 часов бот
предупреждает о завершении через 30 минут. При следующей проверке новый закуп
отменяет прежнее завершение. Если условие всё ещё выполняется, отправляется
новое предупреждение и даётся ещё 30 минут. Учитываются любые закупы, включая
/ludoman, даже если за ними последовали выходы и баланс снова уменьшился.
При банке ровно 2 EUR предупреждение по балансу не отправляется.

Фоновая задача просыпается раз в минуту и выполняет только наступившие проверки;
обычная точность таймера — около минуты. При перезапуске сроки читаются из БД.
Если срок истёк во время простоя, проверка выполняется после запуска.
При ручном завершении старый таймер больше не действует на игру.

Добавлена таблица `game_timeouts`; она создаётся существующим init_db при запуске
бота. Существующие таблицы не изменяются. Перед обновлением сохраните резервную
копию БД. Завершение и запись end_game от имени «Бот» сохраняются одной транзакцией.
При ошибке отправки предупреждения срок сбрасывается и сообщение повторяется
на следующем проходе. Ошибки отправки сообщения об уже выполненном завершении
попадают в журнал; само завершение не откатывается.

Проверено 32 тестами, в том числе: границы 2 EUR и 12 часов, задержка завершения,
повторные отсрочки, закуп с последующим выходом, ручное завершение, восстановление
таймера и ошибка отправки предупреждения. Реальное ожидание 30 минут в тестах
не требуется: время передаётся в проверку явно. На отдельной тестовой игре
проверить доставку предупреждения и работу фоновой задачи после перезапуска.

## Диагностика таймаута и ускоренная проверка пустого банка

В тестовой ветке при банке ровно 0 предупреждение отправляется на ближайшем
минутном проходе, без ожидания очередной 30-минутной проверки. После предупреждения
до автозавершения даётся 2 минуты; новый закуп отменяет завершение. Точность
фоновой задачи — около минуты. Для ненулевого банка и ограничения 12 часов
сохраняется прежний интервал. Уже выданные до обновления предупреждения сохраняют
свой срок; для проверки используйте новую игру либо игру без активного предупреждения.

При запуске через bot_main.py INFO-логи включены автоматически. Логи показывают
старт фоновой задачи, отсутствие активной игры, ID игры, банк, время следующей
проверки, срок завершения, отмену закупом и результат отправки уведомлений.
Просмотр на сервере: `docker compose logs -f --tail=100 python_bot_poker`.
Для проверки: запустить игру с пустым банком, дождаться предупреждения и закрытия;
повторить с закупом после предупреждения и убедиться, что игра не закрылась.
